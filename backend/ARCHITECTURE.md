# Архитектура RAG Playground

## Как проходит запрос

```text
Браузер / тестовый скрипт
    → FastAPI: проверка DEV_ADMIN_TOKEN и владельца чата
    → память: последние завершённые ответы текущего чата с проверкой доступа
    → LLM: уточнение превращается в самостоятельный поисковый запрос
    → BGE-M3: поисковый запрос превращается в embedding 1024
    → PostgreSQL: app.user_id → RLS → hybrid_search
          pg_search (BM25) + pgvector (смысл) → RRF
    → LM Studio / vLLM / Ollama: генерация по найденным фрагментам
    → SSE: части ответа → проверка номеров цитат → финальный ответ
    → PostgreSQL: сохранение вопроса, ответа, статуса и источников
```

## Что хранится в PostgreSQL

- `app_users`, `app_roles`, `user_roles` — пользователи и роли приложения.
- `documents`, `chunks`, `document_roles` — документы, фрагменты, embeddings, доступ.
- `file_sources` — файлы, хеши, signature обработки, состояние и привязка к documents.
- `rag_conversations` — диалог, его владелец и название.
- `rag_turns` — один вопрос и ответ на него, `request_id`, `client_id`, источники,
  статус `generating/completed/cancelled/failed`. В интерфейсе превращается в пару сообщений.

Смена браузера или перезапуск сервера не удаляют историю. Браузер хранит только
текущий интерфейс; токен — в памяти вкладки. Сеансы авторизации пока не реализованы:
есть тестовый выбор пользователя, а не личный вход каждого человека.

## Доступ

`DEV_API_TOKEN` обслуживает прежние endpoints с фиксированным `DEV_USER_ID`.
`DEV_ADMIN_TOKEN` обслуживает `/dev`: он специально разрешает эксперименты от имени
любого активного пользователя. Это административный инструмент, не публичный вход.
Пользователь обычного API не может подставить чужой user_id.

Чаты защищены RLS по владельцу, документы — по ролям. Идентификатор пользователя
устанавливается через `set_config(..., true)` внутри транзакции и не переносится
на следующий запрос пула. Исторический ответ скрывается, если пользователь потерял
доступ хотя бы к одному документу из контекста той генерации.

## Диалоги и параллельность

- Разные чаты генерируют параллельно. Лимит `MAX_CONCURRENT_GENERATIONS=4`
  действует **на процесс**. vLLM может объединять поступающие запросы своим batching.
- При заполненном лимите endpoint отвечает `429`, а не накапливает бесконечную очередь.
- Один чат — одна активная генерация; уникальный индекс PostgreSQL обеспечивает
  это и между несколькими backend-процессами. Повтор в занятый чат даёт `409`.
- `request_id` — UUID операции. Повтор завершённого запроса с тем же текстом
  возвращает сохранённый ответ; другой текст с тем же ID даёт `409`.
- `client_id` — метка источника запроса, не право доступа.
- После аварии backend зависшая генерация может быть освобождена новым запросом
  в тот же чат по истечении lease (1 час). До этого активный запрос даёт `409`.
- Соединение PostgreSQL не держится во время ответа LLM; транзакции короткие.

## Streaming

`meta` содержит ID операции. `sources` — кандидаты, `delta` — черновой текст,
`done` — окончательный ответ. `error` или `cancelled` означают, что ответ не завершён.
После начала SSE HTTP-код уже 200, поэтому нужно проверять сами события.
Отмена закрывает upstream-поток, когда текущая операция чтения вернёт управление;
она не гарантирует мгновенную остановку GPU на стороне сервера модели.

## Память диалога: как реализована

1. `chat_api.py → ChatService.prepare()` резервирует запрос и получает память
   только после проверки владельца диалога.
2. `chat_store.py → memory_history()` читает последние завершённые пары вопрос/ответ
   этого чата. RLS определяет владельца, `visible()` заново проверяет права на документы.
3. `memory.py → bounded_history()` исключает скрытые/незавершённые ответы, оставляет
   до `MEMORY_MAX_TURNS=6` пар в бюджете `MEMORY_MAX_CHARS=6000`. Старые номера цитат
   удаляются: они относятся к другой поисковой выдаче.
4. `ConversationMemory.resolve()` просит ту же LLM вернуть JSON `{"query":"..."}`.
   Если истории нет — дополнительного вызова LLM нет. Если сеть/формат ответа подвели —
   используется исходный вопрос, а в диагностике появляется `fallback` с предупреждением.
5. `chat_api.py` передаёт **одинаковый уточнённый запрос** в BGE-M3 и `hybrid_search`.
6. `generation.py` получает исходный вопрос, уточнённый запрос, ограниченную историю
   и новые фрагменты. История помогает понять разговор, но доказательствами служат
   только документы текущего поиска. Общий бюджет контекста делится между ними.
7. В `rag_turns` сохраняются `retrieval_query`, `memory_turn_ids`, `memory_status`,
   `memory_warning`. Исходный вопрос остаётся в `question`. Документы из использованной
   памяти включаются в `evidence_document_ids`: отзыв доступа скрывает и производные ответы.
8. SSE-событие `retrieval` и окончательный `done` передают диагностику. Интерфейс показывает
   «Запрос для поиска» и число предыдущих ответов. По кнопке «Поиск и память» у старого
   ответа можно посмотреть сохранённый запрос.

Память не является отдельной векторной базой, глобальным состоянием модели или
неограниченным накоплением всех сообщений. Она заново строится для каждого запроса
из PostgreSQL и не смешивается между пользователями/чатами. `/ask` и `/ask/stream`
без ID диалога остаются stateless; память действует на chat endpoints `/dev/conversations/...`.
Настройка `MEMORY_ENABLED=false` отключает её без удаления истории.

У модели может не получиться верно раскрыть неоднозначное уточнение. Проверяйте
поисковый запрос в диагностике; качество нужно оценивать на ваших реальных вопросах.

## Глубокий анализ

`MessageRequest.deep_thinking` выбирает режим **одного сообщения**, не пользователя
и не всего чата. `false` сохраняет быстрый маршрут: память → один поиск → поток ответа
→ проверка номеров цитат. `true` запускает `DeepAnalysis` с отдельным `AnalysisState`:

```text
память → план → поиск → оценка достаточности
                  ↑              │
                  └─ уточнение ──┘  (в пределах max_searches)
                     ↓
               черновик → проверка подтверждений
                     ↑              │
                     └─ исправление ┘  (в пределах retry_limit)
                                    ↓
                         ответ либо отказ с указанием нехватки подтверждений
```

Это явный граф переходов на Python, без дополнительного orchestration-фреймворка.
Единственный инструмент графа — существующий гибридный поиск; LLM не получает
произвольный SQL, доступ к файловой системе или неограниченный набор инструментов.

По умолчанию: 12 шагов, 3 поисковых вызова, 1 переработка ответа, 240 секунд,
до 1500 выходных токенов. Шаги включают память, планирование, оценку, генерацию
и проверку; это не количество внутренних reasoning-токенов. HTTP-вызовам передаётся
оставшееся время, поток проверяет дедлайн при чтении; SQL-поиску — statement_timeout.
Проверки времени кооперативные: служебное освобождение ресурсов и короткие операции
БД могут завершиться после дедлайна, но новый ответ сверх бюджета не подтверждается.

Результаты нескольких поисков объединяются по chunk_id через сумму вкладов
`1/(60+position)`, а не сложением несопоставимых оценок разных запросов.
Каждый поиск получает тот же user_id и проходит через RLS. Все документы,
попавшие в поисковые выдачи и память, записываются в provenance сообщения.

План, оценка достаточности и проверка подтверждений возвращают ограниченные JSON-объекты.
Включён серверный Structured Output; схемы дополнительно проверяются Pydantic.
Некорректный или усечённый ответ валидатора не считается успешным: возможен только
разрешённый повтор, затем отказ. Сбой сети остаётся ошибкой сервиса, а не успешной проверкой.
Модель-валидатор тоже может ошибаться — `validation=passed` означает результат проверки
моделью, а не математическую гарантию достоверности.

Встроенный reasoning отключён на уровне запросов всех Generator, включая суммаризатор
и проверки. Настройки LLM_THINKING и DEEP_LLM_THINKING удалены. Флаг deep_thinking
управляет только шагами графа поиска и проверки.

В БД `rag_turns.deep_thinking` хранит режим, `analysis` — модель, шаги, поисковые запросы,
число повторов, проверок, замечания и время. Внутренние reasoning-тексты не отправляются в UI.
При отзыве доступа история скрывает также `analysis`, поскольку запросы/замечания
могут содержать информацию из источников. Повтор request_id с другим режимом даёт 409.

SSE дополняется событиями `stage`, `search`, `reset`. `reset` удаляет предыдущий
непроверенный черновик перед исправлением. Только `done.answer` считается итогом.
Параллельные чаты имеют независимый state и независимую конфигурацию модели;
глобальная конфигурация shared-клиента не меняется.

## Что ещё не сделано

Пока нет полноценного входа пользователей, production-развёртывания, Markdown-рендера,
сводки всей длинной переписки и проверки качества на размеченном наборе вопросов. После изменения прав
уже открытый текст в браузере не исчезает сам: история проверяется заново при загрузке
или следующем запросе. Чтение памяти и генерация не образуют единую длинную транзакцию.


## Накопительная сводка истории

`app/memory.py` перед уточнением поискового запроса вызывает отдельно настроенный
Generator суммаризатора (`SUMMARY_LLM_*`). Новый экземпляр разделяет HTTP-клиент,
но не меняет основную конфигурацию; дедлайн глубокого режима сохраняется.
Порядок: видимая история → предыдущая сводка + новые пары → короткая сводка →
уточнение запроса → RAG → ответ со сводкой и последней точной парой реплик.

Сводка каждого turn описывает историю ДО его вопроса. Поэтому при следующем запросе
в неё добавляется как минимум собственная пара вопрос/ответ предыдущего turn.
При отсутствии пригодной сводки используется ограниченный хвост последних 20 пар;
бюджет SUMMARY_INPUT_CHARS ограничивает текст, переданный суммаризатору.
Сводка ограничена SUMMARY_MAX_CHARS и SUMMARY_MAX_TOKENS. Возможны потери деталей;
полная переписка хранится отдельно и не заменяется сводкой.

Миграция 005 добавляет memory_summary, summary_status, summary_model. Сводка и
транзитивные evidence_document_ids записываются до генерации основного ответа.
Для следующих запросов выбираются только completed turns своего чата через RLS.
Отзыв доступа к любому документу, использованному в сводке, скрывает её вместе
с ответом. Кэша сводок между пользователями или чатами нет. Сводка считается
недоверенными данными для понимания вопроса, а не доказательством фактов.


Глубокий режим использует дополнительную системную политику частичных ответов
в `app/generation.py`. Оценка sufficient означает достаточность для полезного
ориентира, а не полное покрытие всех частей вопроса. В `Verdict` флаг partial
позволяет принять оговорённые выводы по близким материалам: supported=true и
partial=true дают completed / validation=partial. Один partial=true без supported
не обходит проверку. Обычный режим сохраняет прежнюю политику ответов.
