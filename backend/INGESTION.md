# Импорт файлов в RAG

Все команды запускаются **из папки backend**. Исходные файлы остаются в `app/data`.
Импортер читает их, извлекает текст, получает embeddings у настроенного BGE-M3
и публикует документы в PostgreSQL. Для загрузки языковая модель не требуется.

## Быстрый запуск

Первая установка в другой копии проекта:

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[test,ingest]"
Get-Content -Raw -Encoding utf8 migrations/003_file_ingestion.sql | docker exec -i testagenticrag-db-1 psql -v ON_ERROR_STOP=1 -U rag_admin -d rag
docker build -t rag-doc-converter:local tools/doc-converter
```

В текущем окружении зависимости, миграция и DOC-конвертер уже подготовлены.
Импортер использует существующий административный логин. Он не создаёт постоянные
PostgreSQL-роли и не меняет политики основных таблиц. `rag_reader` продолжает
использоваться только backend, а не импортом.

**Предварительная сверка, без изменения БД и без вычисления embeddings:**

```powershell
.\.venv\Scripts\python.exe scripts/ingest_files.py --database-user rag_admin --prompt-password --report reports/plan.json
```

Введите пароль администратора PostgreSQL: он не отображается и не сохраняется.
Отчёт показывает пути, SHA-256, роли, новые/изменённые/повторные/неизменившиеся файлы
и файлы, отсутствующие на диске. При первом запуске скачивается **только токенизатор**
BGE-M3 в `.cache/tokenizer`; веса embedding-модели здесь не скачиваются.

**Загрузка/синхронизация:** запустите API embeddings в LM Studio, затем:

```powershell
.\.venv\Scripts\python.exe scripts/ingest_files.py --database-user rag_admin --prompt-password --apply --create-roles --report reports/import.json
```

`--create-roles` создаёт только прикладные записи в `app_roles`, отсутствующие
в конфигурации папок; он не создаёт логины PostgreSQL и не назначает роли пользователям.
Для последующих запусков флаг можно убрать, если все роли уже есть.

Другие параметры:

```powershell
# Пробная загрузка первых трёх файлов. Папка всегда сканируется полностью.
.\.venv\Scripts\python.exe scripts/ingest_files.py --database-user rag_admin --prompt-password --apply --limit 3 --report reports/pilot.json

# Принудительная повторная обработка, включая создание embeddings.
.\.venv\Scripts\python.exe scripts/ingest_files.py --database-user rag_admin --prompt-password --apply --force --report reports/reindex.json
```

Для автоматического запуска можно задать `INGEST_DATABASE_URL` существующего
пользователя с необходимыми правами в окружении или `.env`, тогда параметры логина
и запроса пароля не нужны. Это привилегированное подключение: не передавайте его
в браузер, не используйте вместо `DATABASE_URL` приложения.

Коды завершения: `0` — обработка завершена, `1` — отдельные файлы не удалось загрузить,
`2` — общая ошибка настройки/сканирования/подключения. Пропущенные неподдерживаемые
или нераспределённые по ролям файлы перечисляются в отчёте как `skipped`.

## Папки и роли

Конфигурация — `ingest_files.toml`:

```toml
[folders]
employee = ["employee"]
"писатель" = ["писатель"]
example_of_chats = ["example_of_chats"]
```

Вложенные подпапки наследуют роли первой папки. Можно назначить несколько ролей:
`employee = ["employee", "hr"]`. Файлы непосредственно в `app/data` и неизвестные
папки пропускаются. Символические ссылки не индексируются. Исходники, кэш и отчёты
исключены из Git.

Новые роли не назначаются всем пользователям. Чтобы пользователь #1 видел книги,
выполните от администратора (подставьте нужный ID):

```sql
SELECT id,name FROM public.app_roles ORDER BY id;
INSERT INTO public.user_roles(user_id,role_id)
SELECT 1,id FROM public.app_roles WHERE name='писатель'
ON CONFLICT DO NOTHING;
```

Аналогично назначается `example_of_chats`. В веб-чате обновите страницу и подключитесь
снова, чтобы обновился список ролей. Пересчитывать embeddings для назначения роли не нужно.

## Сверка и дедубликация

- SHA-256 вычисляется по байтам файла; переименованная точная копия распознаётся.
- Путь идентифицирует отдельный источник. У копий **разные documents и права**.
  Уже вычисленные векторы копируются, не объединяя доступ разных папок.
- Хеш файла + signature пайплайна определяют необходимость переиндексации.
  Signature учитывает реальный tokenizer.json, версии парсеров, разбиение,
  модель, размерность и `embedding_profile`.
- Если файл и signature не изменились, повторный запуск пропускает embeddings.
- Изменение ролей синхронизирует доступ без embeddings.
- Исчезнувший файл отмечается `missing`; его права отзываются, сами документы
  и фрагменты автоматически не удаляются. При возвращении файла доступ восстанавливается.
  Поэтому перенос из employee в другую папку не оставляет старый доступ employee.
- Неполное сканирование каталога останавливает синхронизацию, чтобы недоступная папка
  не выглядела как массовое удаление. Ревокации не зависят от готовности embedding-сервера.
- Изменённый документ публикуется одной транзакцией после вычисления всех embeddings.
  Ошибка сохраняет прежние опубликованные фрагменты. Успешное обновление заменяет их;
  полного архива всех предыдущих версий пока нет.
- Повторный запуск после сбоя пропускает готовые файлы и повторяет неудавшиеся.
  Для одной коллекции одновременно допускается только один импорт (advisory lock).

Если заменили веса/квантование модели, оставив прежний ID API, измените
`embedding_profile` в TOML и запустите импорт снова. Сходство текста в разных
форматах пока не дедуплицируется: первый этап определяет только точные копии.

## Разбиение и производительность

По умолчанию: `chunk_tokens=500`, `overlap_tokens=80`,
`embedding_batch_size=16`, `file_workers=2`. Границы считаются токенизатором BGE-M3,
не количеством символов. У фрагментов сохраняются страницы PDF, разделы DOCX
и ID сообщений HTML. PDF читается как текст; OCR и анализ изображений не включены.

DOC читается antiword в локальном контейнере без сети с read-only доступом только
к этому файлу. DOCX сохраняет порядок абзацев и таблиц. HTML-архивы разбираются
по сообщениям с заголовками, а не вместе с навигацией страниц; вложения как отдельные
медиафайлы не анализируются.

Если embedding-серверу тяжело, уменьшите `embedding_batch_size` до 4/8 и
`file_workers` до 1. Это не меняет signature и не требует переиндексации.
Для запуска без обращения к Hugging Face после первого скачивания токенизатора
можно установить `HF_HUB_OFFLINE=1`; API LM Studio при этом продолжает использоваться.

## Где что лежит

| Путь | Назначение |
|---|---|
| `app/data/` | Оригиналы файлов по ролям |
| `ingest_files.toml` | Соответствие папок ролям и параметры обработки |
| `scripts/ingest_files.py` | Команда сверки и загрузки |
| `app/ingestion/files.py` | Безопасный обход папок, SHA-256, классификация изменений |
| `app/ingestion/extract.py` | Извлечение текста PDF, DOCX, DOC, HTML, TXT, MD |
| `app/ingestion/chunking.py` | Токенизатор, окна с перекрытием, метаданные и signature |
| `app/ingestion/store.py` | Реестр, права, повторное использование embeddings, атомарная запись |
| `app/embeddings.py` | Одиночные и пакетные запросы к BGE-M3 с проверкой порядка ответов |
| `migrations/003_file_ingestion.sql` | Таблица file_sources и чтение её метаданных с RLS |
| `tools/doc-converter/Dockerfile` | Изолированный конвертер DOC |
| `reports/` | JSON-отчёты сверки и результатов, без извлечённых текстов |
| `.cache/tokenizer/` | Локальный кэш токенизатора |

В PostgreSQL: `file_sources` — реестр источников, `documents` — документы,
`chunks` — текст и векторы, `document_roles` — разрешённые роли.
Пример контроля состояния:

```sql
SELECT collection,status,count(*) FROM public.file_sources GROUP BY collection,status;
SELECT relative_path,status,chunk_count,last_error FROM public.file_sources ORDER BY relative_path;
```

## Проверка в чате

После импорта задайте вопрос по документу с доступной пользователю ролью.
Ссылка источника открывает индексированный текст через
`GET /dev/documents/{id}/text?user_id=...` под административным тестовым токеном.
Backend заново проверяет текущий доступ через RLS; абсолютные пути файлов не выдаются.
В интерфейсе доступны следующие фрагменты. Оригинальные бинарные файлы через веб не публикуются.

Тесты: `tests/test_ingestion.py` — парсеры, сканирование, окна и batch embeddings;
`tests/test_ingestion_database.py` — транзакции, независимые ACL копий, missing/restore.
Реальные проверки включаются через `INGEST_DB_TESTS=1` и `INGEST_DATABASE_URL`;
используются только временные записи, которые затем удаляются.
